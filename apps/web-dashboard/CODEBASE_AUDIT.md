# MobileCloud web console and shared platform audit

**Audit date:** 2026-11-24 · **Source baseline:** `2393ec5` · **Release decision:** hold public or multi-tenant rollout. Existing local-only evaluation should exclude untrusted repositories and use non-production data.

## Remediation status in the working tree

- Public signup, dashboard engine dispatch, outbound webhook delivery, and browser CloudShell are disabled. The engine separates deployment ingress from management; its optional trusted local preview is not a sandbox. W-P1.01 and W-P1.02 are contained, not closed for public builds.
- Local tests exercise session and device revocation, browser-origin and CSRF checks, startup and realtime recovery, and atomic device-code redemption. QR approval now requires proof from the scanning session; that is not hardware identity or attestation.
- All 28 dashboard regression tests and 17 engine tests passed, and the dashboard production build succeeded. Browser checks covered operator sign-in on both loopback addresses, project creation and rejected-draft retention, blocked deployment/build records, realtime, telemetry, and keyboard dialog dismissal. The Deployments route is visible to Git but still needs inclusion in the next commit.
- Keep the rollout hold: isolated workers and tenant authorization, verified production HTTPS/WSS and ingress, migration/backup acceptance, missing storage and product lifecycles, and independent PoR/financial verification are not completed. The evidence below describes the original audit baseline.

## Scope and evidence

Reviewed the Next.js routes and views, API authorization and storage, account and device credentials, QR pairing, the SQLite outbox, WebSocket gateway and browser client, and build/deployment operations. Also reviewed app-facing Rust engine, CloudShell, ingress, and financial-service boundaries; this is not a standalone smart-contract, cryptography, dependency-advisory, or infrastructure audit. The companion [Android report](../../android-app/CODEBASE_AUDIT.md) covers the native client, APK and node runtime. Prior claims were compared with the current source, [README](../../README.md), [realtime design](../../docs/REALTIME-SYNC.md), and [security model](../../docs/SECURITY-MODEL.md). Unrelated template and APK extraction directories, generated assets, local databases, signing material, and live infrastructure were outside scope. No exploit, external scan, or production access was attempted.

## P1 — Block public rollout

| ID | Finding and evidence | Required fix / closure gate |
|---|---|---|
| W-P1.01 | **Public registration can reach an unsandboxed build runner.** Signed-in users can dispatch repository builds when the engine is reachable and configured. The engine runs repository build code under its own identity with inherited environment, before it validates the output. [API login/signup and dispatch](lib/server/api.ts#L304) (304–327, 594–631); [dispatcher](lib/server/builder.ts#L97); [runner](../../core-engine/src/builder/bun_runner.rs#L101) (101–120). | Disable public signup and dispatch by default. Authorize per workspace; use disposable, separately privileged workers with minimal environment, verified artifact transfer, restricted egress, and CPU, memory, disk and time quotas. Require a pass on worker isolation before re-enabling. |
| W-P1.02 | **Tenant identity stops at the dashboard.** Project names are account-scoped in SQLite, but the engine uses bare names for builds, history and rollback. Accounts sharing an engine can collide and alter or see each other's deployment state. The engine's rollback, history and logs lack handler-level authorization; the supplied Caddy fallback forwards management traffic, including from the wildcard tunnel host. [DB](lib/server/db.ts#L21); [API](lib/server/api.ts#L246) (246–254, 634–666); [engine](../../core-engine/src/main.rs#L389) (389–406, 461–474, 589–604); [Caddy](../../config/Caddyfile#L30) (30–59); [tunnel](../../config/cloudflared.yml#L22). | Use stable tenant/project IDs, authorize each management request and rollback target, and serve management routes on a separate private ingress. Check isolation of deploy, logs, history, rollback and cache operations with two separately authorized accounts. |
| W-P1.03 | **Revoking a paired device does not end access.** QR claim creates both a device credential and a separate session. Revocation deletes only the device token. Established sockets are checked at upgrade, not bound to a revocable credential. [API claim](lib/server/api.ts#L396) (396–432); [API revoke](lib/server/api.ts#L1147); [pairing](lib/server/pairing.ts#L435); [gateway](server/realtime.mjs#L92) (92–122, 485–525, 550–589). | Bind the issued session and bearer to the device, revoke together, and terminate or revalidate all matching sockets. Closing the gate requires HTTP and existing/new socket access to stop on revoke, logout and expiry. |
| W-P1.04 | **An unauthenticated handshake parsing failure can stop the gateway.** URL and cookie parsing can throw outside a per-upgrade exception boundary; the launcher stops the web process if the gateway exits. This was identified in source, not exercised. [Gateway](server/realtime.mjs#L91) (91–119, 466–485); [launcher](server/run.mjs#L34) (34–59). | Validate and catch handshake/authentication errors per connection, reject them without process exit, and give the two components independent health/restart supervision. |

## P2 — Trust boundaries and broken core flows

| ID | Finding and evidence | Required fix |
|---|---|---|
| W-P2.01 | **Webhook and repository egress are not restricted.** Webhooks rely on a scheme check and default redirect behavior; repository validation is scheme-based. The control plane and builder can therefore contact services outside the submitting user's trust boundary. [Webhook endpoints](lib/server/api.ts#L945); [delivery](lib/server/identity.ts#L8); [repository policy](lib/server/api.ts#L217) (217–219, 565–568, 600–607). | Enforce destination and redirect policy at connection time and allow only expected egress. Run deliveries asynchronously with bounded time and size. |
| W-P2.02 | **QR approval does not identify the scanning phone.** The approval is bound to a pairing row and QR secret, not to proof of a particular phone's key, and the comparison code is embedded in the ticket. [Pairing](lib/server/pairing.ts#L263) (263–281, 303–309, 337–375); [QR payload](lib/server/qr.ts#L27). | Bind approval and claim to scan-time proof of a device-held key, and derive/show the comparison code on both clients. Keep expiry and single consumption. |
| W-P2.03 | **Secure transport is not a production default.** Session cookies lack `Secure`, the gateway defaults to a plaintext listener, and clients infer a public port from the private gateway port. Android also allows cleartext and its raw TLS socket lacks hostname verification; see [A-P1.03–05](../../android-app/CODEBASE_AUDIT.md#p1--release-blockers). [API cookies/health](lib/server/api.ts#L35) (35–47, 464–477); [gateway](server/realtime.mjs#L31); [browser connection](lib/realtime.ts#L508). | Explicitly configure the approved public HTTPS/WSS origin and path, bind internal listeners privately, set production `Secure` cookies, and verify proxy deployment on both clients. |
| W-P2.04 | **Socket auth lacks browser origin checks; credentials can appear in URLs.** The gateway accepts a query bearer and cookie upgrades without an origin allowlist. The separate CloudShell and core PTY accept a URL credential too. [Gateway](server/realtime.mjs#L91) (91–109, 466–490); [CloudShell client](../../web-cloudshell/src/connection.ts#L23); [PTY auth](../../core-engine/src/terminal_gateway/ws_handler.rs#L41) (41–83). | Allow only canonical browser origins for cookie upgrades. Use a header or short-lived one-use socket ticket, not long-lived URL credentials; redact logs and use a dedicated PTY credential rather than a shared webhook secret. |
| W-P2.05 | **CSRF policy is not tied to the actual credential.** The API can skip CSRF for an Authorization header even when cookie fallback authenticates, or for missing Origin. Login/signup/logout precede the guard. [API](lib/server/api.ts#L71) (71–108, 164–172, 304–334, 438–452, 485–488). | Enforce CSRF for cookie-authenticated writes, validate origin and body type for browser auth routes, and clear session and CSRF cookies on logout. |
| W-P2.06 | **The console password is a UI lock, not API authorization.** Overview and writes are available before unlocking, and a signed-in user can replace or remove the extra password without step-up. [Shell](components/Shell.tsx#L294); [API](lib/server/api.ts#L485) (485–535, 919–943). | Label it as screen privacy only, or bind recent, server-enforced verification to sensitive operations and changes to the protection itself. |
| W-P2.07 | **Abuse limits are incomplete and depend on unverified proxy metadata.** The login/signup limiter trusts forwarded IP and has no eviction; pairing, unlock and failed upgrades lack comparable throttles. [API](lib/server/api.ts#L133) (133–146, 304–344, 353–398, 929–935); [gateway](server/realtime.mjs#L466). | Trust only ingress-sanitized client metadata. Bound state and apply per-account, per-network and per-operation limits with expiry. |
| W-P2.08 | **Device bearers and PATs carry full account authority.** A device bearer lasts a year; PATs may not expire, and bearer authorization is not scoped to a subset of actions. [API](lib/server/api.ts#L485) (485–488, 805–813); [PAT backing](lib/server/identity.ts#L60); [device issuance](lib/server/pairing.ts#L359). | Grant least-privilege scopes, enforce expiry and rotation, and require recent interactive auth for additional credentials or device approval. |
| W-P2.09 | **Web Queue Build sends labels where the API expects an enum.** Both UI choices serialize as display text rather than `web`/`android`. [Build UI](components/PlatformViews.tsx#L178); [API validation](lib/server/api.ts#L1048). | Separate label and value; share the target enum and disable targets without a runner. |
| W-P2.10 | **A project created through the web UI cannot be made deployable from that UI.** There is no repository field or edit flow, and request-deploy sends only the project ID. [Project UI](components/FeatureViews.tsx#L38); [API](lib/server/api.ts#L558) (558–577, 594–615). | Add repository configuration and a create-to-deploy acceptance check after the builder isolation gate passes. |
| W-P2.11 | **Deployments route is missing from a clean checkout.** The Git ignore rule for runtime `deployments/` matches the local app route, which is not tracked although the UI links to it. [Ignore rule](../../.gitignore#L31); [link](components/HomeDashboard.tsx#L68). | Restrict the ignore pattern to runtime output, track the route, and smoke-test all console routes from a clean clone. |
| W-P2.12 | **Legacy installations may retain a public default credential.** The fresh initializer no longer installs it, but the login UI still ships the former prefill and no migration retires it on old databases. [Login](app/login/page.tsx#L10); [initializer](lib/server/db.ts#L336). Exposure applies to affected installs; no live credentials were verified. | Remove the prefill, rotate affected accounts and sessions, and force reset on legacy deployments before public exposure. |

## P3 — Data correctness and recovery

| ID | Finding and evidence | Required fix |
|---|---|---|
| W-P3.01 | **Not all domain writes and outbox records commit together.** Pairing, device, and notification paths can commit before publish; claim can consume the ticket before a usable session is returned. [API](lib/server/api.ts#L353) (353–418, 874–917, 972–976); [outbox](lib/server/events.ts#L72). | Make state, credentials and outbox transactional. Deliver external effects after commit and define recovery for a claim response lost after commit. |
| W-P3.02 | **Account clients treat the global cursor as contiguous, and snapshot/replay can skip changes.** Interleaved accounts trigger false gaps. Startup advances to the welcome watermark after an older snapshot; shared replay/live cursor updates can skip unapplied changes. [Schema](lib/server/db.ts#L258); [gateway](server/realtime.mjs#L512); [store](lib/store.tsx#L195); [browser realtime](lib/realtime.ts#L242) (242–266, 310–365). | Use account-level ordering or an explicit predecessor, a consistent snapshot watermark, and separate replay/live progress until application completes. Do not expose aggregate progress. |
| W-P3.03 | **Fallback recovery can get stranded and wire messages differ.** Polling can report Connected after failed sync; a failed store refresh stops realtime retry. Replay watermark field names and status/ping messages disagree across gateway, browser and mobile. [Browser realtime](lib/realtime.ts#L274) (274–303, 343–406, 434–449, 482–503); [store](lib/store.tsx#L276); [gateway](server/realtime.mjs#L278); [protocol doc](../../docs/REALTIME-SYNC.md#L191). | Keep stale data on transient failure without dropping retry; stop on definitive auth loss. Publish and test a shared protocol version and a consistent heartbeat. |
| W-P3.04 | **Gateway resources and startup recovery are not fully bounded.** Fragmented messages are not aggregate-size bounded, outbound writes ignore backpressure, schema-not-ready opens leak handles, and errors in tailing can exit the process. [Gateway](server/realtime.mjs#L72) (72–85, 194–269, 303–329, 350–357, 538–564, 592–598). | Bound total messages, replay bytes/time, and slow readers; close failed opens and isolate tail retries. Prefer maintained WebSocket framing. |
| W-P3.05 | **Object key collisions can overwrite stored bytes.** The file mapping flattens path separators to a substitute that is itself allowed in names; metadata may record multiple entries for the same file. [Storage API](lib/server/api.ts#L735); [schema](lib/server/db.ts#L64). | Use opaque file names, unique owner/bucket/key metadata, atomic file replacement and strict key/size validation; test on Linux and Windows. |
| W-P3.06 | **API error handling obscures commits and exposes internals.** Raw exception text returns as `400`, malformed JSON becomes an empty object, and telemetry failure in `finally` can mask success after commit. [API](lib/server/api.ts#L117) (117–130, 164–172, 279–296, 698–708). | Validate body schemas and size, use typed public responses, and make telemetry best-effort outside the commit/response path. |
| W-P3.07 | **Device-code redemption is not atomic.** Token creation and approval consumption are separate, and active display codes are not unique. [Identity](lib/server/identity.ts#L85); [schema](lib/server/db.ts#L181). | Atomically consume and issue, enforce active uniqueness and expire unused rows. |
| W-P3.08 | **A refresh failure looks like a failed write.** A successful mutation followed by refresh failure can reject the action and restore a stale snapshot; refresh responses can arrive out of order. [Store](lib/store.tsx#L195) (195–238, 261–274, 293–304). | Separate write success from reconciliation. Apply scoped invalidation and discard stale responses. |
| W-P3.09 | **Browser telemetry is silently rejected.** Page views and Web Vitals bypass the CSRF helper; browser-origin writes are rejected and the caller does not inspect HTTP status. [Shell](components/Shell.tsx#L141); [API](lib/server/api.ts#L1000). | Use the shared authenticated writer and check ingestion in a browser. Distinguish real Web Vitals from approximations. |

## Pn — Follow-up, not verified defects

- Run a separately scoped dependency and secret-history review, and assess rotation for existing deployments. This report did not verify current registries, advisories, or deployed configuration.
- Benchmark at realistic account counts, retention horizons and reconnect concurrency after fixing replay. Add capability-specific rollout criteria rather than treating Vercel parity as a pass/fail test.
- Schedule a signed source-to-release verification for the Rust services and an independent custody/contract review before financial claims.

## What already works, and in what order to proceed

- Most dashboard resource SQL queries and the reviewed realtime event delivery scope data by account. Passwords use salted scrypt and credentials are digested at rest. QR tickets are high-entropy, expire quickly and consume one successful claim transactionally with device creation. Many ordinary writes already commit with outbox entries. These do not resolve the cross-service and revocation findings.
- Since the earlier audit, fresh database initialization no longer seeds the legacy password, the core PTY credential check fails closed, the dashboard has a build dispatcher, and trading invariant arithmetic widens before multiplication. Dispatch existence does not mean build success, and PTY authentication does not by itself justify public ingress. See [DB](lib/server/db.ts#L336), [terminal](../../core-engine/src/terminal_gateway/ws_handler.rs#L41), [builder](lib/server/builder.ts#L97), and [trading risk](../../trading-engine/src/risk_invariants.rs#L70).
- **Release sequence:** isolate builders and management ingress → fix session/QR/transport trust → repair build, deployment and replay flows → test a fresh checkout over production-like HTTPS with both clients. Gate unsupported functionality and financial status independently.
